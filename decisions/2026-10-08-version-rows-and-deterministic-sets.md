# Version rows, mob_new-generated hosts, deterministic sets

- Date: 2026-10-08
- Status: accepted
- Linear: MOB-413 (under MOB-410)

## Context

`2026-10-08-revived-version-rows-ios-selftests-matrix.md` §2–3 decided that
every run resolves a version row (`hex`, `master`, `rc:<repo>@<sha>`) and
records exact versions with its results, that hosts are generated by the
row's own mob_new, and that deterministic named sets run every night beside
the StreamData sweep. This record is how those three land in code.

Until now mob_ci built one host: the fixture harness (`fixtures/_harness`,
`MobCi.Build`) with the five `mob_ci_*` fixture plugins, pinned to whatever
mob/mob_dev the harness's `deps_block` said. Nothing resolved a real
plugin's version, nothing exercised `mix mob.new`, and "which set ran" was a
list of atoms with no name.

## Decision

### `MobCi.Versions` — rows resolve to exact pins before anything runs

`priv/plugins.exs` is the committed list of first-party plugins (a GenericJam
Hex package that ships `priv/mob_plugin.exs`; 25 on 2026-10-08) with their
GitHub repos, in the order every set uses. `Versions.resolve(row, names:)`
turns a row into `%{name => %{version, sha, source, dir}}`:

| row | mob, mob_dev, mob_new, plugins | pin |
|---|---|---|
| `hex` | latest stable on Hex (`hex.pm/api/packages/<name>`) | `{:mob, "== 0.9.14"}` |
| `master` | the remote's default-branch sha (`git ls-remote <url> HEAD`) | `{:mob, path: "<checkout>", override: true}` |
| `rc:<repo>@<sha>` | `<repo>` at `<sha>`, everything else `hex` | mixed |

Git pins are materialised once per sha: one clone per repo under
`~/.cache/mob_ci/repos/<name>` (fetched, never re-cloned) and a detached
`git worktree` per sha under `~/.cache/mob_ci/src/<name>/<sha>`, so two rows
running at once never fight over a working tree and a path dep is immutable
for the life of the result. Hex pins of mob_new and the plugins are unpacked
from `repo.hex.pm` under `~/.cache/mob_ci/hex/<name>-<version>`: mob_new
because it is *run* (`mix mob.new` from inside its source tree, so no global
archive install is needed or shared between rows), the plugins because their
manifests feed P1/P6/P7 and must be the pinned version's, not whatever
sibling checkout `~/code` holds (`MobCi.Plugins.put_resolved_dirs/1`). mob
and mob_dev on Hex are only depended on; Mix fetches them.

Network and disk sit behind `MobCi.Versions.Remote`, a map of four functions
(`hex_latest`, `git_head`, `checkout`, `hex_unpack`), so resolution is
unit-tested with nothing fetched; the git side is tested against a local
repository. Resolvers sharing a cache take a mkdir lock per repo / tarball
(`<cache>/locks`; stale after ten minutes, waiters outlast that), stale
worktree registrations are pruned before a checkout is added, and a tarball
is extracted beside its final path and renamed in, so a half-extracted tree
is never visible. `Versions.record/1` is the serialisable
form stored with results: `%{row: "rc:mob@abc…", repos: %{mob: %{version,
sha, source: "hex" | "git:<url>@<sha>", dir}}}`.

### `MobCi.Host` — the row's mob_new generates the host

A host for (set, row) is `mix mob.new ci_<set>_<row> --blank --android
--no-install`, run from the resolved mob_new's source tree in `MIX_ENV=prod`
(only its runtime deps are fetched), `--local` on `master` with
`MOB_DIR`/`MOB_DEV_DIR`/`MOB_NEW_DIR` pointing at the checkouts (mob_new's
`--local` needs both mob and mob_dev as checkouts, so an `rc:` row generates
non-local and gets its one path dep from the rewrite below). Then:

- `mix.exs`'s `defp deps` is replaced with `Versions.core_deps/1`, the
  generated lines the row doesn't pin (ecto_sqlite3, credo, ex_slop — what
  that mob_new chose; `Host.generated_extras/1`) and
  `Versions.plugin_deps/2`, rendered by `Versions.render_dep/1` (the same
  tuples the fixture harness's `Build.deps_block/3` takes);
- `mix deps.get`;
- `mob.exs` is written with `mob_dir` (`deps/mob` for a Hex mob; the pinned
  checkout on a git row — a `path:` dep never lands under `deps/`, and
  mob_dev's MobDirCheck compares the two), `config :mob, :plugins` (the
  set), `:trusted_plugins` (every activated plugin on the shared release key
  fingerprint mob_new's template pre-trusts) and `:acknowledge_unsafe_plugins`
  (exactly the plugins the row supplies as git checkouts, as mob_new's
  `--local` does; a Hex release is never acknowledged, so one shipped
  without its signature fails the gate here as it does for a user);
- `mix compile`, then `android/local.properties` (sdk, OTP cache, the same
  mob_dir) and `mix mob.icon` — the prep `mix mob.deploy` needs, as the
  fixture harness does.

Generation failures are layer `mob_new`; `deps.get`, `compile` and
`mob.icon` failures are layer `elixir`; the APK build stays
`MobCi.Build.deploy/2`'s. Hosts live under `fixtures/_hosts/<app>`
(gitignored) and are reused for cache only while the same mob_new pin
generated them (`.mob_ci_generator` holds `version sha`; a new mob_new
release or sha regenerates, as does `--fresh`). The fixture harness stays
as is for the fixture plugins — it is the only host that carries a P5
showcase screen; a generated host has none, which P5 must report as a skip
(open, invariants.ex is MOB-412's) rather than push a module that isn't
there.

### `MobCi.Sets` — named, deterministic, committed

| name | plugins | source |
|---|---|---|
| `blank` | none | — |
| `default` | what `mix mob.new` activates | read from the resolved mob_new's `MobNew.ProjectGenerator.assigns/2` by `mix run` in its tree — never hardcoded here |
| `singleton:<p>` | one | — |
| `all` | every buildable first-party plugin | `priv/plugins.exs` |
| `demo` | the first-party part of mob_plugin_demo's activation | `priv/sets/demo.exs` (all 18 committed; the in-tree `mob_demo_*` prototypes have no package) |
| `pairwise:<i>` | row *i* of a committed covering array | `priv/sets/pairwise.exs` |
| `random:<seed>` | 3–8 plugins from the seed | `:rand` exsss, replayable |
| `<file>` | `priv/sets/<file>.exs` | a committed regression set |

Every set draws from the pool `DeviceCaps.buildable(Versions.plugins())`
minus `priv/sets/exclusions.exs`. `device_caps.exs` is the one place that
says a plugin can't be built on the CI host (mob_screencast today);
`exclusions.exs` parks a plugin (`plugin: "F<n>: reason"`) while a known
cross-plugin finding breaks every host that activates it, so `all`, the
pairwise array, seeded and file sets stay buildable. The parked plugin keeps
its `singleton:<p>` (alone it doesn't collide), and `mix ci.device --static`
/ `mix ci.sweep --static` plan with `include_excluded: true`, so the
collision stays on the nightly report until the entry is removed. `all` and
the pairwise rows use the committed plugin order; `default`, `demo` and file
sets keep their source's activation order, since order is part of what an
activation tests.

The covering array is strength 2 over boolean factors: for every two plugins,
all four of {both, a alone, b alone, neither} occur in some row. It is built
greedily — each new row is the best of 2×N candidates (one per starting
factor and starting value, the rest assigned in rotating order by most new
pairs covered, ties to "on") — so it is a pure function of the pool: 11
rows for 23 plugins. `mix ci.sets --regen` is the only writer of
`priv/sets/pairwise.exs`; `test/mob_ci/sets_test.exs` fails when the file is
stale, byte-different from the generator, or leaves a pair uncovered, and
`mix ci.sets --check` says the same from the shell.

### `--set` × `--versions` on the CLI, and results that know their cell

`mix ci.device --set <name> --versions <row>` (either implies the other's
default: `default`, `hex`) plans a `MobCi.Cell`: parse both, resolve the
core, read the set (through the row's mob_new), resolve the set's plugins,
point manifest lookup at them, and print the set with the resolved versions
before anything else. `--static` runs the manifest gate on the pinned
manifests; the device path generates the host and hands it to `MobCi.Run`
as host `:generated`. `mix ci.sweep` takes the same two flags: the pool
becomes the set's plugins on a host generated with the whole set as deps,
and in `--static` mode (where the fixture collision oracle doesn't apply)
it reports every minimal subset `cross_validate` rejects.

`MobCi.Result` gains `set` and `versions`; `Result.stamp/3` fills them on
every result of a cell run and `summary.json` records them. Bad `--set` /
`--versions` values are `Mix.Error`s whose message lists what is accepted;
`--plugins` / `--host` (the harness and sloppy_joe paths) can't be combined
with a cell.

## Consequences

- First real finding of the cell path, on both `hex` and `master`, 2026-10-08:
  `all` is rejected by the static gate because mob_bluetooth and mob_midi both
  declare the iOS plist key `NSBluetoothAlwaysUsageDescription`; the static
  sweep shrinks it to exactly `[:mob_bluetooth, :mob_midi]`. Recorded as
  F9 (MOB-412 slice); `mob_midi` is parked in `priv/sets/exclusions.exs` so
  `all` and the pairwise array (11 rows over 23) build, and the static gate
  on `all` stays red until F9 closes.
- `master` resolution clones 27 repos on first use (about a minute on the
  Mac, cached after); `hex` resolution is 28 API calls and 25 small tarballs.
- The static gate is now version-aware: a sibling checkout under `~/code`
  no longer stands in for a release. Amended 2026-10-09 (MOB-416 follow-up):
  the manifests were the row's but the *validator* was not — `cross_validate`
  ran in mob_ci's VM, i.e. mob_ci's `../mob_dev` (master), so a `hex` row's
  `static` column said what mob_dev master thought. `MobCi.RowValidator` now
  runs it in a throwaway Mix project per mob_dev pin
  (`~/.cache/mob_ci/validators/mob_dev-<hex-x.y.z | git-<sha>>`, built once,
  reused) for a cell's `--static` gate, its P1 static half and the iOS lane's
  gate. The fixture harness, sloppy_joe and the StreamData sweep (which tests
  the validator itself, thousands of calls) keep mob_ci's own mob_dev.
- Open: P5 for generated hosts needs a showcase convention real plugins
  follow (fixtures ship `widget/1`; mob_scene3d doesn't). P12 (MOB-414) will
  call `MobDev.Plugin.SelfTest.run_all/3` on the generated host's node.
- The trust map pins the shared release key and acknowledges only git
  checkouts. A Hex release signed with another key, or shipped unsigned,
  fails the gate at build time — a real finding for a user whose mob.exs
  came from `mix mob.new`, but it blocks the whole set; the plugin's
  singleton isolates it.
- A cell resolves mob_new once: the pin the `default` set was read from is
  the one the host is generated with and stamped as. The greedy array's
  first row is the whole pool, which `all` already builds, so
  `Sets.nightly/0` skips it.
